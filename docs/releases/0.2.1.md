0.2.1 completes native binding forwarding for Dynamic Workers, fixes first-upload SDK typing and same-name R2 recreation, and adds the managed single-domain public gateway. It is for self-hosted operators who need the new Worker Loader behavior or want one public HTTPS domain while keeping `ocd` as the sole application authority.

## What's new

- **Managed single-domain gateway.** `ocd` now owns Caddy as a verified embedded child, projects complete configuration snapshots, serves Worker wildcard HTTPS origins, handles delegated DNS-01 challenges, exposes bounded `ocd caddy` status/validate/reload tools, and recovers the last confirmed snapshot after restart. The Docker qualification environment exercises startup, reload, snapshot recovery, and restart.
- **Dynamic Worker binding forwarding.** Parent Workers can explicitly grant selected private native bindings to Dynamic Workers. Grants use the fork-owned Loader boundary, are immutable per deployment, and are revoked with their owner without broadening the standard structured-clone surface.
- **Dual Worker origins.** Local `.localhost` authority remains available while eligible Workers can also receive a public HTTPS origin under the configured gateway domain. SQLite migration V8 adds the authoritative public-origin state without changing published earlier migrations.

## Before you upgrade

- Stop `ocd` and take a current snapshot before replacing the binary. Startup transactionally applies control migration V8; all previously published migration bytes remain unchanged.
- Existing local Worker origins remain authoritative. Public origins are created only when `[public_gateway]` is configured and the required public DNS and ingress are available.
- A public gateway host must provide routable TCP 443 and delegated UDP/TCP DNS for the configured challenge listener. Docker qualification proves the packaged local topology but does not substitute for public DNS and reachability checks on the deployment host.
- The Caddy and workerd pins are embedded and verified. Production startup remains offline and does not search `PATH` or download runtime components.

## Install or upgrade

An existing receipt-managed installation can upgrade directly:

```console
ocd upgrade 0.2.1
```

For a new user-owned installation, download and review the installer, then pin this release:

```console
curl -fsSL -o install.sh https://raw.githubusercontent.com/elliothux/open-compute/v0.2.1/scripts/install.sh
less install.sh
OPEN_COMPUTE_RELEASE_TAG=v0.2.1 sh install.sh
ocd setup --yes
```

Verify with `ocd --version`, `ocd config check`, `ocd doctor`, `ocd capabilities --json`, and, when the gateway is configured, `ocd caddy status`.

## Security

There are no published security advisories specific to 0.2.1. Dynamic Worker forwarding is grant-based and fail-closed, private values remain outside the standard Loader clone surface, internal gateway sockets remain local and capability-scoped, and Caddy reloads accept only a complete platform-generated configuration after adaptation and validation.

## Known limitations

- Public gateway qualification requires real public TCP 443 plus delegated UDP/TCP DNS; hosts behind non-routable or provider-internal addresses cannot complete public TLS qualification.
- The gateway targets the documented single-machine deployment profile and does not implement Cloudflare's managed multi-region `workers.dev` control plane.
- Dynamic private forwarding is an explicit open-compute extension. It does not claim that native binding objects are structured-cloneable through Cloudflare's standard Worker Loader API.
- The macOS document parser still has no enforceable hard memory ceiling; concurrency, input/output, CPU, and timeout bounds remain active.
- Code signing and macOS notarization are not included.
