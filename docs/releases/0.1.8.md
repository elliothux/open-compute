0.1.8 stops a dynamically loaded child worker from wedging the whole runtime, and moves platform SQLite onto independent Refinery lineages that can adopt an exact 0.1.7 database in place. It also ships the corresponding workerd submodule updates and the bilingual documentation site.

This release is intended for operators who run Dynamic Workers, upgrade an existing 0.1.7 data directory, or need the new Standard resource-limit behavior before putting untrusted Worker code on a shared instance.

## What's new

- Dynamic Workers now enforce the Standard resource-limit profile: 30 seconds of invocation CPU by default (configurable up to 300 seconds), 10,000 subrequests by default (configurable up to 10,000,000), a 128 MiB isolate heap, 1 second of startup CPU, and 6 simultaneous outbound connections. CPU time does not include I/O wait.
- A limit breach or isolate failure condemns that Dynamic Worker isolate, drops it from the loader cache, and fails its in-flight calls. The next call rebuilds the isolate from the immutable version. Neighbor workers and the workerd process keep running.
- If workerd exits, or the process is still alive but the trusted internal data plane stops making progress, the supervisor confirms that runtime generation, revokes its credentials, stops and reaps it, then restarts within the existing backoff budget. `ocd` itself does not restart, and SQLite authority is not rewritten.
- A version upload can set invocation CPU and subrequest budgets in the v4 script metadata `limits` object. Those values are stored on the immutable version and enforced from there. Declaring `limits` in a Wrangler project file is still rejected, so it is not silently ignored. Account Free/Paid plans are not modeled; there is one Standard profile.
- Platform SQLite now uses an independent Refinery lineage per database. An exact 0.1.7 current head is adopted as the V1 baseline and then receives later migrations, including the control database's worker resource-limits migration. Tenant D1 tables and the tenant migration ledger are not treated as platform schema.
- The documentation site has a bilingual homepage and matching English and Chinese docs, including mobile language selection.

The formal pin is now `v1.20260905.0-open-compute-p2.36bf747c`. `workerd --version` still prints `workerd 2026-09-05`; that date string is not the pin. Confirm the upgrade with the pin in `ocd capabilities --json`, not with the workerd date alone. Commits on that range:

- `9ca96ff773a6` — Enforce Workers Standard ResourceLimits for dynamic Workers: per-invocation CPU and subrequest budgets, a 128 MiB isolate heap, a 1 second startup CPU budget, and six simultaneous outbound connections. Over-budget isolates are condemned and evicted so the next call rebuilds from the immutable version.
- `0bf0bd90ee0e` — Merge W2 Standard resource limits enforcement.
- `d379e51bfd2b` — Keep tunneled service interfaces alive. Connection accounting no longer drops the wrapped interface while a `connect()` tunnel is accepted.
- `36bf747c8170` — Capture the invocation limit enforcer so an outbound connection lease uses that invocation's enforcer instead of a later I/O-context lookup.

The four platform binaries under `share/workerd/` were rebuilt from `36bf747c81704f71e2ede6af300fc7fd33b23605`. The embedded Pyodide bundle is unchanged (`314.0.6_2026-08-17_2`).

## Fixed

- An unbounded JavaScript loop in a dynamically loaded child worker no longer wedges the shared runtime until an operator restarts the process. The invocation is terminated, that isolate is removed, and a stuck generation can be recovered without rewriting deployments. This closes [#67](https://github.com/elliothux/open-compute/issues/67).
- A current-head 0.1.7 database is no longer left on the retired migration ledger. Startup adopts that exact head as Refinery V1 only when the previous ledger, checksums, schema, and owner identity all match, then applies later migrations. Drift fails closed instead of committing a partial upgrade. This closes [#51](https://github.com/elliothux/open-compute/issues/51).

## Before you upgrade

- Stop the instance, replace the binary, then start it again. Startup holds the data-directory lock and migrates control before scheduler and resource files. The instance is not ready until every file reaches the new head.
- Only an exact 0.1.7 current head is adopted. Older development databases, checksum drift, partial schema, or a future history fail closed. They are not repaired, rebuilt, or downgraded. Export data you still need before replacing those directories.
- Workers, KV values, R2 objects, D1 tenant tables and rows, Durable Objects, Queues, Workflows, routes, secrets, and immutable deployment artifacts are retained when the adoption checks pass. No manual cache conversion is required for those product records.
- Workers that previously relied on unbounded CPU, subrequests, isolate memory, startup time, or outbound connections will now fail those invocations. A worker that needs more than the 30 second / 10,000 subrequest defaults must set `limits` on a new version upload; a Wrangler project file cannot carry that setting yet.
- Authenticated snapshot restore still requires the snapshot's release and schema identity to match the running binary. A 0.1.7 snapshot is not a 0.1.8 restore source. Take a new snapshot after the upgraded instance is ready.
- `workerd --version` will still say `workerd 2026-09-05` after a successful upgrade.

After replacing the binary, verify the installation with:

```console
ocd --version
ocd config check
ocd doctor
ocd capabilities --json
```

## Install or upgrade

An existing receipt-managed installation can upgrade directly:

```console
ocd upgrade 0.1.8
```

For a new system-wide installation, download and review the installer before elevating it:

```console
curl -fsSL -o install.sh https://raw.githubusercontent.com/elliothux/open-compute/v0.1.8/scripts/install.sh
less install.sh
sudo env OPEN_COMPUTE_RELEASE_TAG=v0.1.8 sh install.sh
sudo /usr/local/bin/ocd setup --yes --system
```

For the default user-owned installation, run the reviewed installer without `sudo`, then run `ocd setup --yes`. The binary and receipt are stored below `$HOME/.local`; configuration and data use the host-standard user directories.

## Security

There are no published security advisories specific to 0.1.8. The resource-limit and generation-recovery changes reduce the impact of a child worker that consumes CPU or stops the trusted data plane from making progress. Isolate limits are not a host sandbox: process and machine isolation remain the operator's responsibility. Database adoption refuses mismatched schema instead of rewriting an unrecognized file.

## Known limitations

- The native macOS document parser still has no enforceable hard memory limit. CPU, input/output, concurrency, timeout, disposable-directory, and cache controls remain active.
- macOS Developer ID signing and Apple notarization are not enabled for this release. Windows and Intel macOS remain source-build-only targets.
- Standard resource limits do not implement Cloudflare Free or Paid account plans, billing, or hosted placement. AI Search remains a bounded single-machine implementation.
