open-compute 0.3.0 adds operator-configured Browser Run and versioned container deployment, and fixes failures exposed by compound Worker workloads. It is intended for single-machine operators who need browser automation or sustained KV, Queue and Durable Object traffic. Browser binaries remain operator-owned; this release does not bundle Chrome or add Cloudflare Containers support.

## What's new

- Browser Run supports managed browser or external CDP backends, tested Puppeteer and Playwright paths, nine Quick Actions, DevTools, Live View and Custom AI. Each managed session owns an isolated temporary context; terminal session history is bounded and persisted in SQLite. Dashboard can configure Browser bindings.
- Versioned runtime and initialization images are published to GHCR for Linux amd64 and arm64 after the stable release succeeds and native empty-volume/restart tests pass. The Compose example runs a non-root daemon with persistent instance authority, explicit authentication tokens and optional external S3 storage; no mutable `latest` tag is published.
- Releases include `test-report.html` and `test-report.json` alongside native executables, `release.json` and `SHA256SUMS`. Reports describe actual qualification, counts and measurements; generating a report does not replace the tests.

## SDK

- Package: `@open-compute/sdk@0.3.0`, paired with `ocd` 0.3.0. Install with `bun add @open-compute/sdk@0.3.0`; published version: [npm](https://www.npmjs.com/package/@open-compute/sdk/v/0.3.0).
- Official management SDK remains `cloudflare@7.2.0`; OpenAPI source remains `cloudflare/api-schemas@780de88d0324b007c907a1782259b1a0e5e87c7d`.
- The cf binding capability contract now advertises the implemented Browser binding. Public Browser routes and the fixed browser clients do not imply that every upstream Browser management method is exposed by the generated management facade.
- Application tooling remains cf `1.0.0-beta.12` and the pinned official Cloudflare Vite plugin v2. Python still requires the documented user-installed PyWrangler build bridge.

## Fixed

- macOS service start no longer terminates a daemon already started by launchd RunAtLoad. Explicit service restart still replaces the running process.
- Durable Object activations no longer occupy the shared 64-entry named WorkerLoader cache. The private facet manager no longer retains its own actor stub, allowing native idle release. Real-daemon regression covers 129 objects and simultaneous hibernatable WebSockets, alarm repair, unrelated Worker availability, version validation and restart with SQLite data preserved ([#146](https://github.com/elliothux/open-compute/issues/146), [#149](https://github.com/elliothux/open-compute/pull/149)).
- Compound RPC and WebSocket operations preserve admission order without serializing completion. Per-object native capabilities remain scoped to their owning activation.
- KV reuses bounded database connections and avoids per-operation WAL recovery/checkpoints. Queue backlog inspection is bounded, occupied consumers respect their batch timeout, and overdue scheduler dispatch waits for admission.
- Readiness remains an admission signal independent of liveness and does not restart healthy processes under load. R2 GET uses authoritative object metadata before body download; artifact HEAD/GET holds the correct read ownership during concurrent writes.
- Container initialization performs a real instance startup before marking a volume ready. Interrupted nonempty volumes are preserved and rejected for recovery; restart retains database, key and instance identity.
- CI caches writable Cargo targets directly, avoiding disk exhaustion while exporting object caches. Stress and release reporting use the current case inventory and preserve failed qualification results.
- Product documentation now removes stale Wrangler claims left in 0.2.4 and distinguishes implemented Browser Run from still-planned Containers.

## Before you upgrade

- **Breaking pre-1.0 deployment identity:** runtime system assets changed. An installation retaining older Worker versions cannot be upgraded in place; preflight rejects incompatible immutable deployment snapshots before replacing the binary or changing authority. Preserve the existing installation, create a separate fresh 0.3.0 installation, transfer application data explicitly and redeploy before switching traffic. Do not delete or reset an old instance to bypass this guard.
- Back up configuration, instance data, SQLite authorities, master keys and object storage. Plan a service restart and keep one daemon owner per scope/data directory.
- This release appends `V15__browser_sessions.sql`. Previously published migration filenames, order and bytes are unchanged. Do not downgrade a migrated data directory.
- Browser is optional and disabled without `[browser]`. Prepare a complete browser installation and specify all capacity/deadline fields before declaring a Browser binding. Chrome is not part of the single-executable payload or the default container image.
- For remote Browser clients, configure the operator-owned `browser.public_origin` and authenticated HTTP/WebSocket proxy paths. Host/Forwarded headers do not determine the public control authority.
- Pin both GHCR images to the same release version. Changes to Compose `.env` do not rotate tokens or reconfigure an already initialized volume. Preserve database and master key together.

## Install or upgrade

For a receipt-managed installation whose retained state passes preflight, after taking a backup:

```console
ocd upgrade 0.3.0
```

For a separate fresh user-owned installation, download and review the pinned installer:

```console
curl -fsSL -o install.sh https://raw.githubusercontent.com/elliothux/open-compute/v0.3.0/scripts/install.sh
less install.sh
OPEN_COMPUTE_RELEASE_TAG=v0.3.0 sh install.sh
ocd setup --yes
```

Check `ocd --version`, `ocd config check`, `ocd instances`, `ocd doctor` and `ocd capabilities --json` before admitting traffic. Follow the [Browser Run guide](https://open-compute.dev/docs/browser-run/) for optional browser setup and the [container example](https://github.com/elliothux/open-compute/tree/v0.3.0/examples/container) for GHCR deployment.

## Security

No security advisory is introduced by this release. Platform listeners require independent authentication; tenant bindings do not expose host credentials, internal tokens, native paths or other instances. Managed browser sessions retain Chrome's native sandbox and bounded CDP/file capabilities, without a `--no-sandbox` fallback. Operators own host network filtering and browser installation security. Production startup stays offline.

## Known limitations

- Browser support covers verified fixed-client paths, not every CDP command or Cloudflare Browser feature. Playwright download events and metadata work, but Worker `saveAs()` and `createReadStream()` do not deliver host Chrome file bytes. Binding `connectionStartTime` is a string and differs from the fixed Playwright number declaration; public v4 uses a number.
- Browser tail and independent browser CPU/memory accounting remain unimplemented. Duration/in-flight metrics are not CPU measurements. External CDP process, profile and filesystem isolation belong to the operator.
- Dynamic Python remains unqualified under the unchanged one-second startup CPU limit. Flask context streaming, Python database drivers/TLS, higher-level AI/API clients and HTTP MCP retain their documented exclusions. The isolated FastAPI 503 did not recur in ten original restart/rollback replays and was accepted on that basis; its original cause was not captured.
- Cloudflare Containers, Sandbox, full Workers for Platforms, general Workers AI inference and other excluded products remain unavailable.
- The platform remains single-machine and self-hosted, without managed multi-region placement or destination filtering per Worker/instance. macOS document parsing has no enforceable memory hard ceiling. Code signing and macOS notarization are not included.

## Verification

Publication requires successful main static CI, 90% Rust line coverage, one complete final workspace Gate with zero ignored cases, controlled Linux egress, three native packaged-executable checks, SDK package verification, the five declared real install/upgrade jobs and stress qualification. The tag workflow collects their actual evidence into the release reports and exposes the GitHub Release only after all required jobs and uploaded-asset verification succeed. Container publication additionally requires native amd64/arm64 startup and restart qualification; a release alone is not evidence of successful GHCR publication.

The scoped 129-object and idle-release regression and ten FastAPI incident replays are historical evidence for their stated paths, not a substitute for this candidate's complete final acceptance or cross-platform release qualification.
