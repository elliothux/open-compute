## 目标与现有边界

宿主 Worker 显式挑选自己持有的完整产品 binding 根对象，Dynamic Worker 获得相同产品 API 和被授权的资源身份；应用无需重写 D1、KV、R2、Queue 等方法。只通过 open-compute 命名空间入口启用。标准 `env.LOADER.get/load` 的 `WorkerCode.env` 仍只传 structured-clone 值与 Service Binding，直接传 D1/KV/R2/Queue 继续抛 `DataCloneError`；不更改 [#91 的合同](implemented/i81-94-cloudflare-api-parity.md)。Cloudflare [Loader API](https://developers.cloudflare.com/dynamic-workers/api-reference/#env-object) 与[普通 binding 传递说明](https://developers.cloudflare.com/dynamic-workers/usage/bindings/#passing-normal-workers-bindings)支持该标准边界；这里的转发是 open-compute 扩展，不声明为 Cloudflare 标准能力。

公开形态沿用 issue 提议的 `getWorker(loader, id, callback)` / `loadWorker(loader, code)`，从 `open-compute:worker-loader` 导入；最终类型只允许把受支持的根 binding 放在 `WorkerCode.env` 顶层。保留原生 Loader 的懒回调、`WorkerStub` 和缓存语义；返回的是等价 API 与资源 authority，不保证跨 isolate 的 JS 对象同一性。普通值、Version Metadata 与原生 `ServiceStub` 按原路径处理。

## 实现边界

1. 在现有 [`createEnvironment`](../packages/runtime/src/loader/wrappers/runtime.ts) 由平台验证过的绑定表包装 transport 为产品 facade 时，记录对象到 `{kind, transport, 构造所需信息}` 的私有弱关联。关联表必须由平台生成的 [`entry.js`](../packages/runtime/src/loader/wrappers/generator.ts) 模块闭包持有；扩展入口只调用该闭包提供的转发操作，不导出注册函数或 raw transport。单靠通用 `createEnvironment` 内的全局弱表不安全：租户可能导入包装函数并传入自造 factory 建立伪造注册。复用绑定类型与构造表、[`modules.ts`](../packages/runtime/src/loader/modules.ts) 的 facade 模块装配；不按业务方法另建 RPC 清单。仅接受此路径创建的真实根对象，拒绝伪造对象、任意实例、Loader、内部 `HOST` 和未支持的类型。
2. 扩展入口在执行原生 `get/load` 回调时，把选定的 transport 作为受限能力送进子 isolate，并生成子 Worker 的 facade wrapper；子代码在首次模块执行前取得已包装的 env。子模块名不能覆盖平台保留路径。已存在的 product transport 持有版本、binding、descriptor、权限和资源身份，最终操作继续由当前后端授权；不按调用者给的 `{kind, resourceId}` 重新查找或扩大权限。
3. **先做真实 workerd 隔离验证**：在子代码顶层 import、`cloudflare:workers.env`、相对导入内部模块、原型修改、RPC 与流操作时，raw transport 和平台内部 env 均不可见。当前 wrapper 的 `createEnvironment` 会从原生 env 复制属性，因此只在 TypeScript 中放置隐藏命名属性不构成隔离。若现有原生 Loader 无法提供不暴露 raw transport 的私有通道，应在 [`third_party/workerd/`](../third_party/workerd/) 增加最窄的 fork 接口，由原生 capability table 承载私有转发；不要放宽标准结构化克隆器，也不要逐一重写产品 binding 序列化。
4. 子请求在自己的执行上下文构造 facade，沿用现有 service scope、输出门、streams、quota 与完成/取消机制。不得把父请求的短期 frame 固化在缓存子 Worker 中。`get` 的 ID 必须覆盖代码、兼容配置、选择的 binding 快照、权限、props 与来源部署；资源重绑使用新 ID。每次新调用仍检查现有资源和来源部署撤销；已接纳调用按现有 drain 规则结束。销毁子 Worker 只释放借用能力及 lease，不删除底层资源。

上述第 3 项是实施前必须过的安全验证点，不是已证实的纯 TypeScript 可行性结论。fork 修改必须按[workerd 路线](workerd/README.md)提交子模块、协调 formal pin、四平台输入和真实运行时验收；开发二进制不能绕过 pin。

撤销审查发现 Worker 删除不会立即把每个保留版本改成 `tombstoned`。KV/R2/D1 等产品 binding 和 Queue 的后端授权会检查已移除的 referrer，Service 会检查来源 Worker 删除状态；Assets、Cloudflare Artifacts、Workflow、Images、自动 Cache 与 AI 文档解析原先只检查版本 `ready`。现已让 Assets manifest/blob、Artifacts 与 Workflow 的后端授权检查所属 Worker 未删除；Images、Cache 与 AI 文档解析复用同一条 live/ready 版本授权查询。保留 `ready` 版本的删除回归测试覆盖了这些共享授权边界、KV 类 binding、Queue producer、Artifacts 和 Workflow。动态子 Worker 的入口级撤销和所有产品的完整真实进程验收仍未完成。

部署切换的 `getWorker` 缓存 ID、可信快照检查和 native namespace key 现均包含来源 route generation。`P23PromotionCoordinator` 与 `VersionController` 的直接部署路径会在提交前调用同一运行时验证接口撤销旧代际前缀；调用失败时不提交部署。撤销前后核对已校验的 workerd startup ID，避免请求落到重启后的另一进程，随后因提交失败而遗留无法恢复的 tombstone。协调器要求提交时的 route generation 与刚撤销的代际一致，防止并发部署漏撤销中间代际。观测设置变更也在增加 route generation 前撤销旧前缀，并用旧代际作为 SQLite CAS 条件。Worker 删除请求撤销整个 Worker 前缀。撤销结果不确定或撤销成功后后续提交失败时，生产 transport 会尝试轮换受监督的 workerd generation，使旧进程的 tombstone 与 stub 一并退出；轮换失败则继续拒绝旧代际，不会重新开放该进程的 prefix。这样，新代际不会误用旧 namespace，而已通过快照校验的旧请求也不能在撤销后重建旧 namespace。正式验收仍须用正式 pin 的真实进程证明旧 stub 的新调用被拒绝、已接纳调用完成，以及失败、并发和重启恢复行为。

源码复查确认 `revokeNamespace` 会把旧 namespace 标记为 revoked、清空 isolate 并从 factory map 删除；旧引用因此被拒绝。现有进程期墓碑进一步拒绝相同 key 的重新创建。`P23PromotionCoordinator::activate_deployment` 与无产品投影的 `VersionController::create_version` 两条部署路径已接入提交前前缀撤销。`VersionPins::fence_and_wait` 不能原样用于普通切换：已开始的 Worker 后台任务被保守保留到 workerd generation 结束，热切换会无限等待或超时。进程轮换恢复已接线，不能只凭源码中的撤销调用认定已通过真实运行时验收。
`handleDispatch` 每次调用都会重新读取并核对快照代际，但在快照核对与 `tenantEnv` 铸造 Loader namespace 之间仍有异步窗口。因此 native fence 必须拒绝旧 key 的**再次创建**，而不只是撤销当时 map 中的实例。若部署 CAS 失败，不能无条件解除旧 key fence：另一并发提交可能已经获胜。
fork 源码现为 `revokeNamespace` 增加进程存活期的 key tombstone，并新增 `revokePrefix`：可以撤销一个 Worker 的所有代际或单一 route generation，已存在的 namespace 被标记为 revoked，未创建的匹配 key 之后也无法创建。key 与前缀 tombstone 合计达到 16K 后 factory 拒绝新 namespace，直到 workerd 重启。Rust namespace 身份和 TypeScript 内部撤销协议、快照校验及定向测试已同步更新；`bun run build`、相关 TypeScript 和 Rust 定向测试通过。private Loader grant 只允许从 factory 向可信 wrapper 转移一次；fork 的 delegation suite 与 private grant transfer 测试已在 Linux arm64 Docker 中通过。正式 pin 的真实产品进程与失败恢复验收尚未完成，因此这套撤销能力尚不能视为 #102 完成。

安全审查发现 fork 的 `WorkerCode.openComputePrivateEnv` 是原生 Loader 字段，不能单靠生成入口的弱关联保证“只有平台登记的根对象可以进入私有通道”。根对象和 Loader grant 的关联表仍只由平台生成的 `entry.js` 闭包持有；先求值的内部转发模块仅导出不持有该表的安全原语及函数，不导出登记表或私有 grant。产品 Worker 的原始 transport 与内部 Cache 已从标准 `env` 移到 handler-only private env，普通声明值及原生 Loader 留在标准 `env`。fork 源码要求调用私有字段的 Loader 带 host-issued grant：静态系统 Loader 可加载产品 Worker，host-only Factory 的 `getPrivate()` 可为受验证的 namespace 铸造 grant，普通 `get()` 给租户的 Loader 调用该字段则拒绝。平台生成 wrapper 只使用隐藏 grant，并要求所选根对象属于同一次原生 env 的 grant 集。同一 Worker 有多个 Loader 时，每个公开 Loader 对应其独立 namespace 的私有 grant。TypeScript 定向测试验证了两个 Loader 的 namespace 选择、跨 env 根对象与伪造 facade 拒绝、生成入口不导出根映射构造器、原始 KV transport 不在 importable env；公开类型编译夹具还断言标准 `WorkerLoaderWorkerCode` 不包含私有字段。fork 的直接调用拒绝与 grant 跨 isolate 传递测试已在 Linux arm64 Docker 中通过，四平台正式 pin 已支持这条路径；真实产品安全资格仍须由最终产品 Gate 关闭。
转发子 Worker 的生成入口不重新导出租户模块的具名成员，防止 `WorkerStub.getEntrypoint(name)` 绕过 facade 包装取得原始 handler env。当前扩展只声明默认入口；具名入口需另行明确列出、包装并验证后才可加入支持范围。

隔离复查发现正式 stock workerd 允许租户模块顶层改写 `WeakMap.prototype.get`（`.temp/i102-monkeypatch-probe/` 的真实进程返回 `{"changed":true}`）；原路径的 TypeScript 探针因此能把未登记对象伪造成 KV 根对象，结果为 `forgery accepted`。现已把弱登记、描述符 Map 操作及原生 Loader 的 `get/load` 方法捕获放入先于租户模块求值的内部模块；生成入口和子 Worker wrapper 的授权路径使用捕获的方法，env 包装也不再依赖租户可改写的 WeakSet/Object 原型方法。公开 Loader 方法与内部源码表在租户求值前固定，所有平台 facade 和 DO/Workflow wrapper 也先于租户模块求值。子 wrapper 使用只处理已选根对象的生成路径。KV、R2、D1、DO、Queue、Service facade 保存原始 transport 的私有 WeakMap，以及 Service scope、运行时上下文、DO 内部能力和 Workflow 触发器的权限关联，均改为自身持有捕获的方法，防止租户改写 `WeakMap.prototype.get/set` 截获或伪造能力。原始 `env` 复制和转发模块条目改用索引读取，避免租户改写数组迭代器观察 handler-only transport。`.temp/i102-import-order-probe/` 的正式 stock workerd 实进程在租户同时篡改 WeakMap 与 Loader 原型后仍返回 `{"root":true,"tenant":true,"child":"ok"}`；TypeScript 回归确认伪造对象无法进入私有 env，私有 WeakMap 和数组迭代器不泄漏 KV transport。`bun run build`、运行时类型检查和定向测试通过；正式 fork 已编译并完成原生跨 isolate 隔离测试，完整产品调用仍待最终 Gate 验证，因此扩展仍不可发布。

正式 stock workerd 的 `.temp/i102-extension-probe/` 进一步验证了 `open-compute:` 模块到生成入口的相对导入、两级原生 Loader 以及无转发资源时的子 Worker 调用，响应为 `nested-ok`。该探针没有产品 binding；它不能替代 fork private env 隔离与产品行为验收。子 Worker 不借用父 Worker 的内部 Cache transport，当前扩展路径中的 Cache API 会明确报 `CACHE_UNAVAILABLE`，自动缓存保持关闭。

`getWorker` 的 ID 合同与原生 Loader 一致：在同一来源版本内，同一 ID 必须始终对应相同的动态代码、兼容配置、普通 env 值和所选 binding 快照；任一项变化时调用者必须使用新 ID。平台键前缀另加入来源 Worker version、route generation 与 WorkerCode digest，隔离来源部署变化。原生 `get` 命中缓存时根本不执行回调，因此三参数 API 无法核对“本次回调将选择什么”；错误复用 ID 会取回旧 Worker，这一行为已由定向测试固定。需要每次按可变输入重建子 Worker 时使用 `loadWorker`。公开类型只有在正式 fork pin 与真实进程验收完成后才可发布，并须把同一 ID 的不可变约束写入其 JSDoc；来源撤销场景仍待验收。

## 支持面与完成标准

首批用同一个机制跑通实际 Preview 所需的 D1、KV、R2、Queue producer；随后按 issue 的完整根对象矩阵补齐 Images、Vectorize、AI Search、Artifacts、DO namespace、Workflow binding、Service/native `ServiceStub`、Assets、AI 和 ordinary values。每个产品复用**已支持**的 facade 方法及权限；未实现的方法明确失败。D1 session、prepared statement，R2 body/multipart，Images pipeline，DO stub/storage、Workflow instance/step、`ExecutionContext` 和 `waitUntil` 等中间对象不可直接转发，子 Worker 通过根对象重新创建它们。转发既有 DO namespace 或 Workflow definition 不等于动态注册类、Alarm、Cron、Queue consumer 或可恢复 Workflow 定义。

验收以正式 pin 的真实进程完成：同一 guest 源码在直接部署和动态加载下比较产品行为；D1 session/bookmark/batch、KV metadata、R2 streaming/multipart、Images 链、AI Search streaming、Service fetch/RPC/props 分别覆盖成功与拒绝。再覆盖双账户隔离、同代码不同 binding、改名/重绑、warm/cold 缓存、父请求结束、来源部署撤销、取消/重启、伪造根对象、内部模块访问和流背压。标准 Loader 的 `DataCloneError` 正反用例保留。发布类型、能力说明与示例前，记录装配、冷启动、热请求和流式内存的实测；没有证据不承诺零拷贝或无额外开销。
